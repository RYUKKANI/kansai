# 메일을 사용할 수 없는 관계자의 비밀번호 지원

`scripts/reset-staff-password.mjs`는 **프로젝트 관리자 본인의 신뢰한 기기와 대화형 터미널**에서만 사용하는 선택적 운영 도구입니다. 이 CLI 자체는 공개 재설정 API나 일회용 지원 링크를 추가하지 않습니다. 별도의 [기기 연결형 Owner 복구](STAFF_AUTH_REBUILD.md)는 확인된 프로젝트 관리자의 제어면 승인 후 같은 브라우저에서 사용할 수 있습니다. 이 문서와 격리 검사는 운영 계정의 비밀번호가 실제로 변경됐다는 증거가 아닙니다.

후속 [Owner 전용 계정 관리](OWNER_ACCOUNT_MANAGEMENT.md)에는 인증된 Owner만 사용하는 비공개 웹 초기화 경로가 있습니다. 그 화면의 현재 세션·MFA·최근 인증 조건과 결과 불명 처리 계약은 별도 문서에 따릅니다. 아래의 터미널 실행·기기 제한은 이 CLI 도구에 대한 설명입니다.

기존 Supabase Auth UUID에 공식 `auth.admin.updateUserById(userId, { password })`만 호출합니다. 비밀번호 저장·검증·해시는 Supabase Auth가 수행하며, 도구는 `auth.users`에 직접 쓰지 않습니다. 이메일·확인 상태·역할·실명·공개 동의·콘텐츠를 변경하거나 기존 사용자를 삭제·재생성하지 않습니다.

## 실행 전 확인

- 실제 Supabase 프로젝트 관리 권한을 가진 운영자가 기존 계정 UUID와 현재 활성·승인 상태를 대조하고, 지원 요청자 본인임을 별도 경로로 확인합니다. 사용자 이름이나 이메일 앞부분으로 실명을 추측하지 않습니다.
- 지원 대상 본인이 새 비밀번호를 직접 숨김 입력할 수 있는 관리자 기기를 준비합니다. 운영자에게 새 비밀번호를 채팅·이메일·문서로 보내도록 요청하지 않습니다.
- 승인된 지원용 DB migration과 아래의 두 service-only RPC가 적용된 환경에서만 실행합니다. RPC가 없거나 대상을 확인할 수 없으면 도구는 Auth 변경 전에 중단합니다.
- 서버 전용 secret/service key를 가진 프로젝트 관리자는 RLS를 우회할 수 있습니다. 일반 관계자용 도구나 계정 관리 권한으로 배포하지 않습니다. 실제 담당자의 플랫폼 계정을 검증하지 못한 상태를 특정 구단 관계자의 수동 작업으로 기록하지 않습니다.

Android 휴대전화 브라우저에서 이 Node 터미널 도구를 실행할 수 있다고 가정하지 않습니다. Supabase Dashboard에 이메일 없이 새 비밀번호를 직접 입력하는 기능이 있다고 안내하지 않습니다. 휴대전화에서는 이 CLI 대신 후속 기기 연결형 복구를 사용합니다. 해당 기능이 실제 배포됐는지와 프로젝트 관리자의 별도 승인 가능 여부를 확인합니다.

## 사용 순서

Node와 저장소의 고정 의존성이 설치된 기기에서 다음 명령만 실행합니다.

```bash
node scripts/reset-staff-password.mjs
```

명령 인자로 비밀번호·키·대상 정보를 넘기지 않습니다. 파일·표준입력 파이프에서 비밀번호를 읽는 기능도 없습니다. `--help`만 별도로 지원합니다.

1. 이미 대조한 정식 `https://<project-ref>.supabase.co` 프로젝트 URL을 입력하고 호스트 이름을 다시 입력합니다. 이 제한된 도구는 임의 호스트·사용자 정의 Auth 도메인·로컬 서버로 서비스 키를 전송하지 않습니다.
2. 서버 전용 secret/service key를 숨김 입력합니다. 신뢰한 프로세스 환경에 이미 설정된 `SUPABASE_SECRET_KEY` 또는 `SUPABASE_SERVICE_ROLE_KEY`도 사용할 수 있으나, 명령 줄에 값을 직접 붙여 넣어 셸 기록에 남기지 않습니다. `SUPABASE_URL`은 정식 프로젝트 URL을 지정할 수 있습니다. 키를 `.env`, Git, 화면 캡처나 지원 기록에 새로 저장하지 않습니다.
3. 실제 기존 계정 UUID를 입력합니다. 서버가 현재 활성·승인된 관계자인지 확인한 뒤 최소 권한 정보만 표시합니다. 대상을 다시 확인하고 **같은 UUID를 직접 재입력**합니다.
4. 별도 본인 확인을 마친 뒤 사유 코드 `credential_recovery` 또는 `operator_requested_password_reset` 중 하나를 직접 입력합니다. 자유 서술·연락처·비밀번호를 감사 사유에 복제하지 않습니다. 필요한 본인 확인 근거는 정해진 별도 운영 기록에서 최소 범위로 관리합니다.
5. 대상 본인이 새 비밀번호와 확인 값을 숨김 입력합니다. 최소 12자이고 UTF-8 인코딩 기준 최대 72바이트여야 합니다. 한글·가나·한자 등은 한 글자가 여러 바이트일 수 있습니다. 실제 프로젝트의 Supabase 비밀번호 정책도 적용됩니다. 기존 비밀번호를 알아야 할 필요는 없습니다.
6. 대상 상태를 다시 조회하고, DB의 요청 기록이 확인된 경우에만 공식 Auth 비밀번호 변경을 한 번 호출합니다. 반환 UUID와 최종 감사 기록까지 확인한 경우에만 완료를 표시합니다.
7. 대상 본인이 실제 배포 관리자 주소에서 기존 아이디와 새 비밀번호로 로그인합니다. UUID·권한·콘텐츠 연결과 이전 세션의 처리를 실제 환경에서 확인합니다. 새 비밀번호를 운영자나 AI에 보고하지 않습니다.

숨김 입력은 화면에 문자를 표시하지 않으며 Ctrl+C로 취소할 수 있습니다. JS 문자열이 프로세스 메모리에서 즉시 완전히 지워진다는 보장은 하지 않습니다. 도구 사용 후 프로세스를 종료하고 공유 기기를 사용하지 않습니다. 새 비밀번호를 도구 실행 화면과 함께 녹화하지 않습니다.

## 서버 경계와 감사

| 경로                                                                              | 동작과 제한                                                                                                                                                                                                                       |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `staff_auth_support_password_target(p_user_id)`                                   | service role만 호출하며 현재 활성·승인된 기존 관계자를 검증합니다. UUID·권한·승인·활동 상태만 반환하고 이메일이나 비밀번호 매핑을 제공하지 않습니다.                                                                              |
| `staff_auth_support_password_audit(p_user_id, p_operation_id, p_state, p_reason)` | service role만 호출하는 지원 요청·결과 기록입니다. operation UUID에 대상·고정 사유 코드를 연결하고 `requested` 뒤 `succeeded`, `failed`, `indeterminate` 중 하나로 기록합니다. 비밀번호·토큰·키·변경 전후 값은 저장하지 않습니다. |
| `auth.admin.updateUserById(userId, { password })`                                 | 공식 Auth 서버가 같은 UUID의 비밀번호만 처리합니다. 브라우저 publishable key로 이 관리자 API를 제공하지 않습니다.                                                                                                                 |

지원 이력은 대상 계정이 실행한 것으로 표시하지 않습니다. 확인할 수 없는 인간 작업자는 `actor_id`, 실명, 요청자 UUID를 비워 두고 `source=system_support`, `executor=project_admin_password_support_cli`로 구분합니다. 서버가 확인할 수 있는 범위는 서비스 자격으로 실행한 지원 작업이며, 프로젝트 관리자 기기를 누가 조작했는지까지 증명하지 않습니다. 정해진 별도 운영 기록과 Supabase 플랫폼 감사 로그를 함께 확인해야 합니다.

DB의 요청·최종 기록과 Supabase Auth 변경은 **서로 다른 트랜잭션**입니다. 성공 감사는 신뢰한 도구가 받은 Auth의 성공 응답에 대한 기록이며, DB 자체가 Auth 응답을 독립 검증하는 것은 아닙니다. 오류를 억지로 성공으로 기록하거나 실행자 UUID를 사칭하지 않습니다.

## 불확실한 결과의 처리

| 결과                                               | 다음 동작                                                                                                                                                        |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 대상·UUID 확인·사유·비밀번호 확인·요청 감사가 실패 | Auth 변경을 호출하지 않습니다. 잘못된 대상이나 환경을 수정한 뒤 처음부터 검토합니다.                                                                             |
| Auth가 비밀번호 정책 등 명확한 4xx 응답으로 거절   | `failed`를 기록하고 성공으로 표시하지 않습니다. 원문 오류·비밀번호를 출력하지 않습니다.                                                                          |
| Auth 네트워크 오류·서버 오류·반환 UUID 불일치      | 반영 여부를 단정하지 않고 `indeterminate`를 기록합니다. 자동 재시도하지 않습니다. 표시된 operation UUID로 Auth 로그와 지원 기록을 대조합니다.                    |
| Auth 성공 후 최종 감사 응답 불명                   | 비밀번호는 변경됐을 수 있음을 명시하고 전체 완료로 표시하지 않습니다. 성공 감사가 이미 저장됐을 가능성도 있으므로 새 operation으로 재설정부터 반복하지 않습니다. |

결과 조정은 확인된 프로젝트 관리자가 Auth 감사 로그, 대상 UUID, 지원 operation 상태를 대조한 뒤 별도 운영 절차로 수행합니다. 지원 도구에 결과를 임의로 확정하는 공개 API나 재시도 옵션은 없습니다. 확인하지 못한 요청을 성공으로 정리하지 않습니다.

## 세션과 메일에 관한 실제 한계

공식 Auth 서버 소스에서 관리자 비밀번호 변경은 `user.UpdatePassword(tx, nil)`로 이어지고, 현재 구현은 전체 세션을 로그아웃시키는 경로를 사용합니다. 그러나 이미 발급된 JWT는 만료까지 유효할 수 있습니다. 즉시 차단이 필요하면 서버·RLS에서 JWT의 `session_id`가 `auth.sessions`에 남아 있는지 추가 검사해야 하며, 이 CLI 자체가 그 검사를 추가하지는 않습니다. 후속 `staff_live_session_authorization` migration을 적용하면 앱의 공통 DB 역할·본인 프로필 경계가 실제 세션을 검사합니다. 실제 배포 Auth 버전과 세션 설정에서 이전 refresh token·access token 동작을 검증해야 합니다.

이 경로는 `/recover` 메일 발송을 사용하지 않습니다. 다만 프로젝트에서 비밀번호 변경 알림 메일을 켠 경우 Supabase가 별도 알림을 보낼 수 있습니다. 알림 설정을 끄거나 이메일 소유 확인이 완료됐다고 표시하는 작업은 하지 않습니다. 메일 발송이 없는 비밀번호 변경 API라는 점과 시스템 전체에서 메일이 한 통도 나가지 않는다는 보장은 구분합니다.

현재 도움말의 비밀번호 설정은 현재 비밀번호 또는 서버가 서명한 최근 PKCE 복구/초대 인증을 요구합니다. 일반 OTP 세션·URL의 `type=recovery`·브라우저 이벤트만으로 제한을 풀지 않습니다. 공식 Auth `verifyPost`와 implicit 경로는 일반 OTP 인증을 발급하므로, 관리자 `generateLink`를 단순히 기존 복구 화면에 연결해 작동한다고 안내하지 않습니다. 공개 지원 링크 방식은 이번 도구에 포함하지 않습니다.

## 근거와 검증 범위

- [공식 updateUserById API](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid): 서버 측 기존 UUID의 비밀번호 변경 지원.
- [공식 Auth 관리자 구현](https://github.com/supabase/auth/blob/master/internal/api/admin.go), [User.UpdatePassword 구현](https://github.com/supabase/auth/blob/master/internal/models/user.go): 비밀번호 정책·네이티브 처리·세션 정리 경로.
- [공식 세션 문서](https://supabase.com/docs/guides/auth/sessions): JWT 만료와 세션 조회를 통한 추가 차단의 차이.
- [공식 verify 구현](https://github.com/supabase/auth/blob/master/internal/api/verify.go): PKCE 복구와 일반 OTP 발급의 차이.

`node --test tests/staff-password-support.test.mjs`는 모의 SDK 응답·실제 숨김 입력 함수·비대화형 실행 거부를 검사합니다. 실제 운영 비밀번호 변경, Android 실행, 메일 알림, 세션 회수는 수행하지 않았습니다. 해당 검증 전에는 실제 복구 완료로 보고하지 않습니다.

후속 Owner 웹 관리가 추가된 뒤의 통합 회귀도 이 CLI 검사를 포함해 통과했습니다. check 72개 파일 오류·경고·힌트 0개, build/export 32페이지·32개 HTML, 기존 화면 fixture 빌드 통과, SQL 409개·Node 171개 통과/6개 건너뜀/실패 0개이며 별도 새 화면 통합 6개도 통과했습니다. 이는 실제 CLI 비밀번호 변경을 실행했다는 뜻은 아닙니다. 정확한 명령과 남은 실제 시험은 [Owner 검증 결과](OWNER_ACCOUNT_MANAGEMENT.md#검증-결과)를 확인합니다.
