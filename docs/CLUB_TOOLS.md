# 채팅과 당일 훈련 출석

관리자 메뉴의 **팀 채팅**과 **오늘 훈련 출석**에서 사용합니다. 가입 승인과 활성 계정이 필요합니다. 이메일이나 공용 계정을 새로 만들지 않으며 기존 계정 UUID·등급·선수 연결을 유지합니다.

## 방과 권한

| 등급 | 선수방 | 총괄·스태프방 | 당일 출석 |
| --- | --- | --- | --- |
| 총괄 | 조회·전송·삭제 | 조회·전송·삭제 | 활성 선수 명단 확인·정정 |
| 스태프 | 접근 불가 | 조회·전송 | 활성 선수 명단 확인·정정 |
| 선수 | 조회·전송 | 접근 불가 | 연결된 본인 선수의 출석 체크·조회 |
| 승인 대기·정지·권한 회수·만료 세션 | 접근 불가 | 접근 불가 | 접근 불가 |

총괄의 메시지 삭제에는 이유가 필요합니다. 원문은 지우고 삭제 표시를 남깁니다. 삭제 이력은 총괄만 조회합니다. 일반 계정은 메시지·알림·출석 표에 직접 쓰거나 작업자를 지정할 수 없습니다. 수정 가능한 Auth metadata는 권한 근거로 사용하지 않습니다.

메시지는 2,000자, 계정당 1분 20건으로 제한합니다. 동일 전송 nonce 재시도는 새 글을 중복 생성하지 않습니다. 서버에서 확인한 작성자 UUID·당시 확인된 실명·등급을 저장합니다. 실명이 미확인된 계정은 이름을 추측하지 않고 미확인 관계자로 표시합니다. 이름·메시지는 HTML로 해석하지 않습니다.

Realtime은 `public.office_chat_events`의 새 알림만 전송합니다. 이 표에는 방·알림 ID·시각만 있고 본문·작성자·출석은 없습니다. 방별 RLS로 현재 접근을 검사한 뒤 본문은 인증 RPC로 다시 읽습니다. WebSocket은 설정된 Supabase 프로젝트 한 곳만 CSP에 허용합니다. 연결이 끊겨도 주기적 재조회와 수동 갱신을 제공하며, 계정·방 전환 시 구독과 비공개 화면을 정리합니다.

## 출석 운영

1. 총괄·스태프가 기존 훈련 관리에서 날짜와 시간을 등록합니다. 공개 홈페이지 게시 여부와 별개로 승인된 관계자는 당일 훈련의 제목·시간·장소·진행 상태만 확인합니다. 내부 메모는 보내지 않습니다.
2. 총괄은 멤버 관리에서 선수 계정에 **기존 선수 기록**을 연결합니다. 계정 UUID와 선수 ID는 서로 다릅니다. 연결되지 않은 계정이나 비활성 선수는 본인 체크를 할 수 없습니다. 스태프 가입 때문에 선수 기록을 만들지 않습니다.
3. 선수는 일본 시간(Asia/Tokyo)의 당일 `개최 예정` 훈련에서 본인 출석을 체크합니다. 같은 체크를 반복해도 한 건이며, 자동 결석 처리나 위치 수집은 없습니다.
4. 총괄·스태프는 당일 훈련의 출석·지각·결석·공결을 이유와 함께 기록합니다. 취소 훈련과 과거·미래 훈련은 이 화면에서 변경할 수 없습니다. 선수가 운영진의 결석·공결 기록을 직접 덮어쓰지 못합니다.

기존 `private.attendance`의 복합 기본 키와 과거 출석을 유지합니다. 새 작성자·기록 시각·본인 체크 시각만 추가하고, 과거의 알 수 없는 작성자는 소급 지정하지 않습니다. 출석 변경과 감사 기록은 한 트랜잭션으로 확정합니다. 실패한 저장은 성공 표시나 성공 이력으로 남기지 않습니다. 출석 감사 상세는 운영진만 조회하며 선수에게 다른 사람의 출석이나 명부를 노출하지 않습니다. 자유 입력 이유에는 건강 정보·연락처·인증 정보를 입력하지 않습니다.

## 보관과 한계

채팅·출석·감사 로그의 보관 기간과 정리 승인 담당자는 아직 확정되지 않았습니다. 이번 마이그레이션에는 기존 기록 삭제나 예약 일괄 정리가 없습니다. 이를 무기한 보관 정책으로 간주하지 않습니다. 운영자가 목적별 기간, 백업 기간, 삭제 승인·실행 이력을 결정한 뒤 별도 정리 절차를 추가해야 합니다. 총괄의 명시적 메시지 삭제는 즉시 본문을 제거합니다. 전송 본문 전체는 감사 로그에 복제하지 않습니다.

계정 정지·권한 회수는 서버 재조회·전송·RLS에 즉시 적용됩니다. 이미 읽은 내용을 외부에 저장한 사본까지 회수하지는 못합니다. DB 소유자의 직접 SQL, DDL, 트리거 우회, 외부 배포는 일반 업무 RPC 감사 범위 밖입니다. 실제 Supabase Realtime 전달은 배포 환경에서 별도 확인해야 하며 로컬 PGlite는 논리 복제를 실행하지 않습니다.

## 적용·검사·복구

- 새 마이그레이션 `20261017105633_club_chat_and_training_attendance.sql`을 권한 검사 후 적용합니다. capability가 확인된 DB에서만 메뉴가 나타납니다. 새 표 외의 기존 publication 설정을 바꾸지 않습니다.
- `npm run test:chat`, `npm run test:attendance`로 각 파트를 따로 검사합니다. 회원창 수정은 `members`, CSP 수정은 `security`, 검사 등록은 `tooling`과 함께 확인합니다. 공통 컴파일은 `check`, `build`, `export:preview`로 확인합니다.
- 문제가 발생하면 사이트의 이전 정상 커밋을 재배포해 메뉴 진입을 되돌립니다. 추가 DB 표·열과 기존 데이터를 삭제하지 않습니다. RPC 차단이 필요하면 운영 변경 기록을 남기고 새 마이그레이션에서 해당 권한·capability를 회수합니다. 재시도 전에 적용한 마이그레이션 목록과 publication을 확인합니다.
