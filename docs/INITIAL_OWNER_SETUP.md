# 기존 단독 총괄의 초기 등록

기존 총괄 계정 하나만 남아 있고 관계자 정보 전환이 끝나지 않은 경우를 위한 유지보수 절차입니다. 로그인 아이디·계정 UUID·기존 권한·비밀번호·선수 연결은 바꾸지 않습니다. 일반 회원의 가입 승인이나 자기 실명 확인을 허용하는 기능이 아닙니다.

## 확인 출처

| 출처 | 의미 | 사람 확인자 |
| --- | --- | --- |
| `initial_owner_setup` | 기존 단독 총괄이 요청한 최초 등록을 유지보수 작업으로 완료 | 없음. 다른 사람이 심사했다고 표시하지 않음 |
| `staff_review` 또는 기존 확인 기록 | 다른 총괄이 구단 관계자와 실명을 확인 | 기존 계정 UUID와 서버 시각 |
| 확인 기록 없음 | 이름을 저장했으나 확인 절차는 미완료 | 없음 |

초기 등록 시각은 시스템이 등록을 완료한 시각입니다. 신분증이나 외부 신원 인증을 거쳤다는 뜻이 아닙니다. 내부 표시 이름과 공개 홈페이지의 이름·사진 게시 동의는 계속 별개입니다.

## 실행 조건과 절차

1. 실제 배포 주소와 연결 프로젝트를 확인합니다. 대상자의 명시적인 요청과 초기 등록 안내 확인을 먼저 확보합니다. 요청이 없으면 실행하지 않습니다.
2. 대상이 기존의 활성·승인된 단독 총괄인지, 계정 UUID·현재 아이디·현재 등록 이름이 일치하는지 읽기 전용으로 대조합니다. 미입력 이름이나 담당 업무를 추측하지 않습니다.
3. 테스트를 통과한 migration을 적용합니다. 초기화 함수는 비공개 스키마의 유지보수 전용 함수이며, `PUBLIC`·비로그인·로그인·서비스 API 역할에는 실행 권한이 없습니다. 브라우저 버튼이나 가입 API에 연결하지 않습니다.
4. 유지보수 연결에서 `private.initialize_legacy_owner_identity`를 호출합니다. 예상 UUID·아이디·등록 이름, 명시적 안내 확인, 요청 참조와 사유를 전달합니다. 입력한 예상값과 실제 계정이 다르면 중단합니다.
5. 동일 트랜잭션에서 초기 등록 증빙과 작업 이력을 남깁니다. 실제 수행 주체는 AI 보조 DB 유지보수이고 사람 확인자는 만들지 않습니다. 요청자는 명시적으로 요청한 기존 계정으로 구분합니다.
6. 등록 완료·확인 출처·감사 기록을 조회하고 기존 UUID·권한·Auth 계정 및 업무 데이터가 유지됐는지 대조합니다. 사용자가 페이지를 다시 열면 서버의 현재 상태를 읽습니다.

초기 등록은 한 번만 가능합니다. 같은 요청의 반복, 다른 대상, 신규 회원, 정지 계정, 여러 총괄이 존재하는 경우에는 이 경로를 사용하지 않습니다. 안내 확인 없이 미완료 프로필을 완료 처리하지 않습니다. 담당 업무가 미입력인 경우에는 빈 값으로 남기며 총괄 등급은 기존 권한에서 표시합니다.

## 이후 변경과 복구

초기 등록 후 본인의 확인된 이름을 바꾸려면 기존 정정 심사 절차를 따릅니다. 다른 총괄이 정상 확인하면 출처는 일반 관계자 확인으로 바뀌고 초기 등록 증빙은 과거 기록으로 남습니다. 초기화 함수를 재실행하거나 증빙을 삭제해 같은 절차를 반복하지 않습니다.

UI에 문제가 있으면 검증된 정적 UI로 복구합니다. 이미 확정된 등록·권한과 감사 이력은 UI 복구를 이유로 되돌리거나 삭제하지 않습니다. 잘못된 이름의 정정은 별도 요청과 기존 심사 절차로 처리합니다.

초기 등록 증빙에는 기존 감사·계정 기록과 같은 접근 제한 및 보관 정책을 적용합니다. 보관 기간이 별도 확정되지 않은 상태에서 임의의 자동 삭제나 무기한 보관 승인을 추가하지 않습니다. 직접 DB 권한을 가진 운영자는 추적 장치를 변경할 수도 있으므로 유지보수 계정 자체의 접근과 작업 내역은 별도로 관리해야 합니다.
