# 관계자 인증·복구 재점검 (2026-10-16)

기존 Auth 계정·UUID·아이디 연결·권한·콘텐츠·감사 기록을 보존하는 추가 migration입니다. 기존 migration을 수정해 다시 적용하거나 계정을 삭제·재가입시키지 않습니다. 실제 사용자의 비밀번호를 코드·SQL·문서에 넣지 않습니다.

## 확인한 원인과 수정

| 문제 | 수정 |
| --- | --- |
| Auth 메일 429·SMTP/네트워크 장애를 접수 성공으로 반환 | 안전한 제한/장애 코드로 응답. 계정 미존재는 일반 응답으로 유지하며 메일 주소·제공자 원문을 공개하지 않음 |
| 실패한 재전송이 이전 메일의 PKCE verifier를 덮어씀 | 고정 SDK의 흐름별 verifier와 `sb_flow_id`를 연결. 서버는 고정 복귀 주소에 검증한 불투명 ID만 추가 |
| 저장 중 토큰 갱신으로 확인된 저장 결과가 사라짐 | 인증 상태와 저장 작업 결과를 분리. 다른 계정으로 바뀌면 그 계정의 세션을 정리하지 않음 |
| 빈 응답·`success:false`를 저장 완료로 표시 | 작업별 성공 코드와 구조를 확인. 전송 후 시간 초과·5xx·비정상 응답은 결과 불명이며 자동 재전송 금지 |
| 유일한 Owner가 잠기면 현재 비밀번호와 메일 없이 복구 불가 | 아래의 기기 연결형 프로젝트 관리자 지원 절차 추가 |
| Auth 세션 삭제 후 기존 access JWT로 콘텐츠 접근 | 공통 DB 역할 검사에 실제 `auth.sessions` 존재·사용자·만료·Auth 정지를 검사. 예약 작업용 역할 계산은 별도로 유지 |
| 가입 생성 실패도 접수 성공으로 표시 | 같은 UUID 생성과 DB 확정까지 확인한 경우만 생성 완료. 확정 실패는 결과 불명. 명확한 생성 거절의 미사용 예약만 안전하게 해제 |

일반 OTP나 URL의 `type=recovery`만으로 비밀번호 변경을 허용하지 않습니다. 공식 Auth v2.197.0의 PKCE 복구는 서명된 `recovery` AMR을 유지하지만 implicit/일반 OTP는 다릅니다. MFA·현재 비밀번호·재인증의 네이티브 거절도 유지하며 안전한 안내를 표시합니다. MFA 설정 제거·우회는 추가하지 않습니다.

## 이메일 없는 유일 Owner 복구

이 절차는 익명 신청자의 자동 본인 인증이 아닙니다. **프로젝트 관리 권한을 이미 가진 신뢰된 담당자**가 별도 본인 확인 후 특정 요청을 승인합니다. 일반 운영진·로그인한 Owner·service key만으로 이 승인을 호출할 수 없습니다. Owner가 여러 명이면 기존 Owner 전용 계정 관리를 사용합니다.

1. 본인이 관리자 도움말의 **메일을 받을 수 없는 최고 관리자 복구**를 열고 기존 아이디로 신청합니다. 휴대전화에서도 같은 브라우저와 탭을 유지합니다.
2. 브라우저가 256비트 기기 비밀값을 생성합니다. 서버는 독립 목적 HMAC만 저장하고, 원래 값은 이 탭의 `sessionStorage`와 HTTPS 요청 본문에서만 사용합니다. 새 Auth 세션이나 내부 권한은 발급하지 않습니다.
3. 본인은 **신청 UUID와 공개 기기 확인 번호만** 확인된 프로젝트 관리자에게 전달합니다. 기기 비밀값·비밀번호·서비스 키는 전달하지 않습니다.
4. 프로젝트 관리자는 본인 확인, 실제 프로젝트, 기존 계정 UUID, 현재 유일한 활성·승인 Owner 상태, 화면의 신청 UUID와 기기 확인 번호를 대조합니다. 아이디만 보고 승인하지 않습니다. 같은 계정의 미해결 `executing` 작업을 먼저 조사합니다.
5. 신뢰된 프로젝트 제어면의 `postgres`로 아래 함수를 호출합니다. 실제 값은 운영 도구의 입력이며 저장소·PR·감사 사유에 복사하지 않습니다.

```sql
select private.approve_staff_support_recovery(
  '<REQUEST_UUID>'::uuid,
  '<VERIFIED_EXISTING_OWNER_UUID>'::uuid,
  '<PUBLIC_DEVICE_REFERENCE_16_LOWERCASE_HEX>',
  'credential_recovery'
);
```

6. 본인이 같은 탭에서 **관리자 확인 상태 새로고침**을 누릅니다. 요청은 10분, 승인 후에는 원래 만료 이내 최대 5분만 유효합니다. 화면은 서버의 실제 승인 만료 시각을 표시합니다.
7. 본인이 새 비밀번호·확인 값을 직접 입력하고 저장합니다. 서버는 승인·기기 증명·현재 Owner 상태를 재검사하고 `executing`을 먼저 확정한 뒤 공식 `auth.admin.updateUserById(기존 UUID, {password})`를 한 번만 호출합니다.
8. 같은 UUID의 Auth 성공과 최종 감사까지 확인한 경우만 저장 완료를 표시합니다. 본인이 기존 아이디와 새 비밀번호로 로그인해 UUID·권한·기존 콘텐츠를 확인합니다. 비밀번호를 AI나 운영자에게 알려주지 않습니다.

새 기능을 배포했다는 사실만으로 실제 계정 복구가 완료되지는 않습니다. 실제 새 비밀번호 입력·저장·로그인 성공 증거는 별도로 확인합니다.

### 서버 경계

요청·상태·실행·결과 RPC는 service role 전용이며, 승인은 **private 스키마의 `postgres` 전용 SECURITY INVOKER 함수**입니다. 공개 승인 함수·username→이메일 조회·비밀번호 테이블을 만들지 않습니다. 틀린 아이디도 같은 신청 형태를 받지만 승인할 수 없습니다. 기기 확인 번호는 별도 HMAC의 일부이며 DB 증명값과 다릅니다.

입력 allowlist, 본문 크기 제한, 공유 제한, 아이디/신청별 제한을 적용합니다. IP를 검증할 수 없는 구성에서는 전달 헤더를 신뢰하지 않습니다. 기기 증명 비교는 고정 길이 전체 바이트를 확인합니다. 승인·claim은 현재 계정을 다시 확인하고, 기존 Owner 웹 초기화와 같은 대상의 `executing` 상태가 겹치지 않게 잠급니다. 익명 대기 신청은 대상 계정을 잠그지 않습니다.

상태는 `requested → approved → executing → succeeded|failed|uncertain`입니다. 성공 요청을 새 비밀번호로 재전송해도 그 값을 다시 적용하지 않습니다. 응답 유실·함수 중단·감사 확정 불명은 수동 대조 대상입니다. 브라우저는 전송 시도를 먼저 저장해 새로고침 후 재전송을 막고, 상태 조회로 확정 결과만 확인합니다.

Auth 변경과 감사 DB는 서로 다른 트랜잭션입니다. 프로젝트 관리자는 확인되지 않은 결과를 성공으로 정리하지 않습니다. 기존 CLI·직접 Auth Admin·DB 관리자 작업은 프로젝트 관리 권한으로 별도 실행할 수 있으므로 이 웹 잠금이 모든 외부 경로를 강제한다고 주장하지 않습니다. 외부 지원 도구를 쓰기 전에는 진행 중인 웹 operation을 조사해야 합니다.

### 감사·보관

신청·승인·실행·결과는 `source=project_admin_recovery`로 구분합니다. 실제 사람을 증명할 수 없어 인간 actor/요청자 UUID와 실명은 비워 두고, 실제 실행자는 `project_admin_control_plane` 또는 `staff_auth_edge_function`으로 기록합니다. 기존 과거 작업자를 임의로 특정 이름에 연결하지 않습니다. 비밀번호·토큰·기기 비밀·증명 HMAC·연락처의 변경 전후 값을 기록하지 않습니다.

10분 만료는 사용 가능 기간이며 데이터 삭제 기간이 아닙니다. 신청 레지스트리와 감사에는 기존의 목적·담당자·접근·보관 기간·백업/삭제 검토 정책을 적용합니다. 보관 기간이 아직 승인되지 않았으므로 임의로 무기한 보관을 승인하거나 자동/일괄 삭제를 추가하지 않았습니다. 반복 신청은 제한되지만 행은 쌓일 수 있어 담당자가 운영 보관 정책을 정해야 합니다. 정리는 미해결 executing/uncertain 조사와 감사 연결 보존 후 별도 승인 절차로 수행합니다.

## 검증과 실제 환경의 구분

`npm run check`, `npm run build`, `npm run export:preview`, 기존 화면 호환 빌드, 전체 SQL·Node 검사를 실행합니다. 새 검사에는 메일 실패, 재전송 후 이전 verifier 유지, 저장 중 토큰 갱신, 거짓 성공 차단, 종료 세션 RLS, 기기 증명 위조·승인 ACL·만료·중복 실행·감사 불명과 세 언어 UI가 포함됩니다.

`npm run test:auth:native`와 별도 **Verify native staff authentication** CI는 고정 CLI 2.121.0으로 폐기할 로컬 DB·GoTrue·Mailpit·Edge를 생성합니다. 실제 메일 복구/PKCE/비밀번호 저장, 이전 비밀번호 거절, 같은 UUID 로그인, 실제 미승인 사용자 RLS, 관리자 승인 복구와 완료 요청 재사용을 검사합니다. 운영 프로젝트 키나 실제 계정을 쓰지 않습니다. Docker가 없으면 성공/건너뜀 대신 명확히 실패합니다. 실제 CI 통과 여부를 확인하기 전에는 네이티브 통합 성공으로 보고하지 않습니다.

운영 SMTP 전달, 실제 Android 기기 입력·저장, MFA step-up UI와 실제 사용자의 새 비밀번호 로그인은 별도 수동 확인 항목입니다. 메일 없는 지원 절차가 메일 공급자의 발송 한도를 고치는 것은 아닙니다. 일반 메일 복구를 안정적으로 운영하려면 별도 SMTP 설정이 필요할 수 있습니다.

## 전환과 복구 순서

1. 실제 저장소·배포 주소·Supabase 프로젝트, 기존 UUID/Owner 수/콘텐츠 수를 읽기 전용으로 확인합니다. **같은 배포 트리의 PR 검사와 실제 네이티브 Auth 통합이 모두 성공한 뒤에만 DB·Edge·UI 변경을 시작합니다.** 이전 migration을 다시 적용하지 않습니다.
2. 새 migration 세 개를 순서대로 적용합니다: live session authorization → device-bound owner recovery → registration reservation release. 로컬 파일 시각과 MCP 기록 시각이 다를 수 있으므로 이름과 내용을 함께 대조합니다.
3. 같은 커밋의 `staff-auth`와 상대 모듈 전체를 배포합니다. 기존 공개 동작 때문에 `verify_jwt=false`는 유지하되 각 비공개 작업의 검증을 그대로 둡니다. 새 서버 비밀키는 필요 없습니다.
4. PR 검사와 네이티브 통합이 성공한 동일 트리의 정적 UI를 배포합니다. 실제 Site URL이 현재 도메인인지, 고정 도움말 복귀 주소와 origin 설정이 맞는지 확인합니다.
5. 일반/Owner 권한·익명 API 거절·기존 콘텐츠를 재확인하고, 사용자에게 새 비밀번호 입력 단계만 넘깁니다. 실제 로그인 확인 전 완료라고 보고하지 않습니다.

문제가 발생하면 새 도움말 UI와 gateway를 검증된 이전 버전으로 되돌립니다. 새 승인 호출을 중단하고 미해결 작업을 먼저 조사합니다. live-session 검사는 인증 경계 강화이므로 단순 UI 롤백을 이유로 해제하지 않습니다. 새 DB 행·감사·기존 계정과 콘텐츠를 삭제하지 않습니다. 이미 반영됐을 수 있는 Auth 변경은 UI 롤백으로 취소되지 않습니다.
