# 한 화면에서 선수·프로필·사진 등록

## 사용 방법

관리자 **선수 관리 → 새 등록**에서 내부 선수 이름·활동 상태, 홈페이지 표시 이름·로마자 이름·포지션·등번호·소개, 사진을 같은 양식에 입력합니다. 목록의 **편집**도 같은 양식으로 열립니다. 별도의 선수 사진 창이나 공개 프로필 창으로 이동하지 않습니다.

사진은 등록된 선수 사진을 선택하거나 이 양식에서 직접 업로드합니다. 새 파일의 사진 제목·설명·촬영일도 여기에서 입력합니다. 새 사진은 `player` 카테고리로 자동 분류하고 내부 선수와 공개 프로필에 함께 연결합니다. 파일 선택 시에는 미리보기만 표시하며, 저장 버튼을 누를 때 비공개 Storage에 업로드합니다.

**선수·프로필·사진 저장**은 비공개 초안으로 함께 저장합니다. **승인 대기로 저장**은 프로필을 승인 대기로 저장합니다. Owner·Administrator는 동의를 확인하고 **게시**를 누르면 사진과 프로필을 함께 승인합니다. 저장 성공과 홈페이지 재빌드 완료는 별도의 상태로 표시합니다.

프로필을 아직 입력하지 않은 경우에는 내부 등록과 사진 초안만 저장할 수 있습니다. 프로필 일부를 입력했다면 공개 이름과 포지션을 완성해야 합니다. 프로필 URL은 최초 게시 후 변경할 수 없습니다. 기존 선수 UUID도 유지합니다.

## 권한·저장 규칙

- 내부 선수 정보, 공개 프로필, 미디어는 기존의 분리된 테이블을 유지합니다. 화면과 저장 동작을 합칩니다.
- `save_player_office` RPC는 호출자 권한으로 실행하고 기존 RLS·동의 검증·게시 트리거를 적용합니다. 작업 중 오류가 발생하면 모든 DB 행 변경이 취소됩니다.
- 사진 업로드가 끝났으나 DB 저장이 실패한 경우 파일은 비공개로 남습니다. 같은 양식에서 다시 저장하면 파일을 중복 업로드하지 않습니다. Storage와 PostgreSQL은 서로 다른 서비스이므로 파일 업로드 자체는 DB 롤백 대상이 아닙니다.
- 새 양식의 UUID를 저장 재시도에도 유지합니다. 저장 결과를 받지 못한 뒤 재시도해도 동일 선수가 중복 생성되지 않으며 최신 내용을 열도록 안내합니다.
- 동시 편집 시 선수·프로필·사진의 갱신 시각을 비교합니다. 변경된 내용을 이전 값으로 덮어쓰지 않습니다.
- 공개 프로필과 내부 등록 사진이 기존에 다른 경우, 사진을 다시 선택하기 전까지 각각의 연결을 보존합니다.
- Coach는 등록과 프로필 초안·승인 대기 저장, 승인된 선수 사진 선택을 할 수 있습니다. 사진 업로드·승인과 프로필 게시 권한은 추가하지 않습니다. Editor는 내부 선수 관리에 접근하지 않습니다.
- 프로필 공개 동의와 사진 공개 동의·게시 권한을 확인해야 게시할 수 있습니다. 미확인 자료를 자동 공개하지 않습니다.
- 공개 승인 자료만 기존 `kansai-sub` 수집 작업에 포함됩니다. 내부 이름·동의·초안은 수집하지 않습니다.

## 편집 위치와 검증

화면 구성은 `src/scripts/admin-player.ts`, 공통 사진 처리는 `src/scripts/admin-photo.ts`, 진입·저장 연결은 `src/scripts/admin.ts`에서 관리합니다. 일본어를 기본으로 한국어·영어 번역은 `src/data/locales/messages.json`에서 편집합니다.

DB 저장 함수는 `player_single_form` 마이그레이션에 있습니다. 기존 테이블이나 RLS를 초기화하지 않습니다. SQL 검사는 `supabase/tests/player-form.test.mjs`, 실제 관리자 스크립트의 양식·사진·저장 재시도 검사는 `tests/player-office.test.mjs`에서 수행합니다. 테스트 자료는 격리된 DB·메모리에만 생성합니다.
