# 운영진 identity 검증표

이 표는 사용자 요청의 **12개 수용 기준**을 기준으로 합니다. 기존 계정·콘텐츠를 보존하는 검증이며 운영 계정 변경이나 임의 수신자 메일 발송을 허가하는 문서가 아닙니다. 구현 파일·실행 명령·결과는 최종 코드 확인 후 아래 증거 표에 기록합니다.

`격리 자동`은 PGlite·가짜 Auth/SDK·메모리 DOM 등 실제 서비스와 분리된 검사입니다. `실제 테스트 배포`는 별도 테스트 프로젝트의 Auth·메일·프록시·배포 URL과 브라우저 검증입니다. 자동 테스트가 통과해도 실제 테스트 배포 항목을 통과로 표시하지 않습니다.

## 수용 기준별 필수 시나리오

| 번호 | 수용 기준 | 격리 자동 검사 | 실제 테스트 배포와 완료 증거 |
| --- | --- | --- | --- |
| 1 | 기존 계정은 같은 UUID·역할로 아이디 로그인 | 기존 역할 계정만 enrollment 허용; 정규화 아이디 매핑; 중복 경합; 이메일에서 이름 추측 없음; 새 선수 생성 없음 | 기존 초대·기존 비밀번호 계정 각각 로그인 전후 Auth UUID·역할·콘텐츠 연결 동일; 실제 Owner 성공과 세션 복원 |
| 2 | 미승인은 내부 데이터 접근 불가 | 이메일 확인 전·후, 실명 미확인, 승인 대기·거절·정지 각각 본인 상태만 허용; 명부·비공개 기사·선수·일정·미디어·감사·Storage 직접 접근 차단 | 새 계정 이메일 확인만으로 승인되지 않음; 직접 Auth 가입으로 만든 orphan 계정도 권한 없음; 공개된 사이트 정보만 읽기 가능 |
| 3 | 직접 API 승인·역할 우회 불가 | 자기 승인·자기 실명 확인·원하는 역할 강제·Owner 과권한 부여·마지막 Owner 비활성화·`user_metadata` 위조·테이블 직접 DML·RPC 이름 우회 거절 | publishable key·실제 JWT로 REST/RPC/Storage 호출; 게이트웨이 경유와 직접 Auth endpoint 경로 비교; 요청 body에 미허용 필드 거절 |
| 4 | 아이디 중복·동명이인·이메일 변경 처리 | 아이디 대소문자·공백·최소/최대 길이·허용 문자·동시 예약·확정 경합; 동일 Unicode 실명 서로 다른 UUID 허용; 이름 변경 본인 신청·타인 검토; 기존 이메일 가입 탈취 차단 | 실제 Auth 이메일 변경 후 확인 전후 로그인·복구; 고유 username 유지; 예전 이메일로 타인 연결 불가; 신청 이름과 승인 이름 상태 명확 |
| 5 | 실제 URL에서 비밀번호 설정·복구 | 비밀번호 확인 불일치·길이; Auth 오류 일반화; 세션 없는 변경·위조 claim·다른 UUID·오래된 복구 인증 거절; 실제 현재 비밀번호 검사; 브라우저 PKCE 검증기 비전송·S256 challenge 계약 | 허용된 테스트 수신자만 사용; 신규·기존 passwordless 초대, 만료·재사용 링크, 잘못된 redirect, 같은 브라우저 PKCE 코드 교환·AMR, 다른 브라우저·검증기 삭제·복구 새 요청, 복구 후 새 비밀번호·기존 세션 정책, Owner 복구 성공 |
| 6 | actor 위조로 타인 이력 생성 불가 | 클라이언트 actor/name/role/실행자 필드 거절; 감사 DML 금지; 서버 UUID·당시 승인 이름 snapshot 확인; 메타데이터 위조 무효 | 두 테스트 운영진으로 서로 바꿔 요청해도 자기 서버 신원으로 기록; 자동화의 알려진 실행자·요청자 분리; 직접 SQL의 귀속 한계 문서화 |
| 7 | 생성·수정·발행·삭제에 실명 감사 | 실제 트리거·RPC로 4작업 수행 후 UUID·확인 이름·당시 역할·시각·엔터티·ID·변경 필드·허용 마스킹 값·사유 확인; 이름 변경 전후 과거 snapshot 유지 | 기사·선수·일정·미디어 각 실제 저장/발행/철회/허용 삭제 확인; 서비스 자동발행과 사람이 요청한 작업의 표시 구분 |
| 8 | 실패 저장에 성공 이력 없음 | RLS 실패, 승인 거절, 무효 입력, 강제 트랜잭션 롤백, 복합 선수 저장 실패에서 업무 행·성공 감사 모두 미반영 | 네트워크 오류·Auth 만료·제약 오류·중복 제출에서 성공 표시와 감사 수 일치; 실패 보안 이벤트를 성공 변경 이력과 구분 |
| 9 | 로그 읽기로 개인정보 누출 없음 | Owner/Administrator/Editor/Coach/미승인/익명 역할별 엔터티·본인 범위; 금지 필드·이메일·전화·토큰·본문 전체 없음; 명부에 이메일 없음; XSS 문자열은 textContent | 실제 REST 응답과 화면 모두 확인; 승인자 정보·내부 실명 노출 범위 검토; 로그 내 검색·페이지 이동도 같은 필터 유지 |
| 10 | 정지·역할 회수는 기존 세션에도 적용 | 이미 발급된 JWT로 정지/강등 후 다음 읽기·쓰기·발행·Storage·RPC 제한; 마지막 Owner 보호; 동시 관리자 변경 경합 | 로그인 상태의 다른 탭·기기에서 정지/해제/강등; 역할 변경 후 새 허용 범위 확인; Auth 세션 회수 정책과 DB 즉시 제한 별도 기록 |
| 11 | 기존 기사·선수·일정·미디어 정상 | 기존 전체 SQL/UI 회귀, 원본 콘텐츠·사진·UUID·공개 동의 보존, 공개 빌드·오프라인 export·권한 경계 | 기존 업무 한 건씩 실제 테스트 환경에서 저장·조회·발행·취소; 비공개 원본이 공개 artifact에 포함되지 않음; 이전 Owner fallback도 검증 |
| 12 | 일본어·한국어·영어·모바일 정상 | 언어별 로그인·가입·상태·복구·명부·이름 변경·감사 문구, 레이블·오류·키보드·초점·재시도·필드 값 보존; 토큰이 언어 URL로 복사되지 않음 | 실제 모바일/데스크톱 브라우저, 320px/375px/가로 화면·확대·키보드·일본어/한국어/영어; 남색·파랑 로고 첫 화면, 아이디/비밀번호/가입 중심, 별도 도움말 복구 |

## 요청의 추가 경계와 공격 입력

| 항목 | 확인할 입력·상황 | 기대 결과 |

| 롤백 | 새 로그인/복구 실패·승인 정책 오류·잘못된 Origin | 새 UI·등록 중지, 기존 Owner 경로 유지, UUID·콘텐츠·원본 감사 보존; DB 초기화/계정 재생성 없음 |
| 기존 초대 혼용 | 새 DB와 이전 초대 함수·빈 capability·정지된 기존 세션 | 보호 함수 먼저 배포; 새 DB/빈 권한 응답에서는 메일 전송 전 거절; 이전 역할 직접 DML을 복구하지 않음 |

## 이메일 확인 생략 정책의 후속 검사

사용자 선택에 따라 새 포털 가입의 확인 메일을 생략합니다. 실제 연락 이메일과 기존 Auth UUID는 유지하고, 공개 Auth의 전역 Confirm Email은 유지합니다. 아래 시나리오는 원래 표의 이메일 확인 항목에 추가되는 새 정책 검사입니다.

| 경계 | 후속 검사와 기대 결과 |
| --- | --- |
| 네이티브 계정 생성 | 고정 SDK가 `/auth/v1/admin/users`만 호출; 이메일 확인 API·signup/OTP API 호출 없음; `email_confirm=true`와 신뢰한 app_metadata 표식; 일반 응답에 세션·UUID·메일 없음 |
| 승인 대기 | native 자동 확인만으로 역할 생성 없음; 직접 API·RLS는 본인 신청 상태만 허용; 승인된 수동 정책은 메일 확인 표시가 false여도 현재 활성 역할로 업무 허용 |
| 생성/확정 경합 | 확정 전 또는 실패한 Auth 계정이 다른 아이디로 enrollment해 정책을 바꾸지 못함; 기존 역할만 enrollment; 메타데이터·reserved username·UUID·이메일·생성 시각 불일치 거절 |
| 관계자 승인 | 메일 생략 계정은 Owner만 승인; 자기 승인 금지·마지막 Owner 보호 유지; Owner만 대기 신청 연락 이메일을 별도 조회; 승인 전 관계·실명·신청 ID·실제 연락 주소를 외부 경로로 대조 |
| 확인 상태 정직성 | `not_required`는 메일 소유 미확인으로 표시; native 자동 확인이나 user_metadata 위조를 실제 소유 확인으로 표시하지 않음; 일반 명부·감사에는 이메일 미노출 |
| 남용 제한 | 기존 DB HMAC 식별자·전역 제한 유지; CAPTCHA 정책 미설정 가입 차단; CAPTCHA 실패가 공유 생성 한도를 소모하지 않음; 검증 후 공유 생성 시도 10회/시간 |
| 새 비밀번호 | 최소 12자와 native 최대 72 UTF-8 바이트; 한글 24자/25자 경계; 기존 로그인 비밀번호 검증은 변경하지 않음 |
| 메일 없는 지원 | 본인이 신뢰한 관리 기기에서 숨김 입력; 같은 UUID에 공식 `updateUserById`; service-only 대상·지원 감사; 요청→성공/실패/불확실, 재사용·actor 위조·중복 성공·미확정 성공 표시 차단 |
| 실제 서비스 한계 | 프로젝트 Auth health v2.197.0 확인. 실제 신규 운영 가입·Owner 로그인·지원 도구의 운영 실행은 별도 결과로 기록; 단위 검사나 버전 확인으로 통과를 대체하지 않음 |
