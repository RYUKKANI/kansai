# V3 2단계 — 콘텐츠 운영

뉴스 검색·카테고리·미리보기·대표 사진·갤러리·기존 발행 권한은 V2 구현을 사용합니다. 중복된 콘텐츠 편집기를 만들지 않습니다.

## 이번 구현

| 기능 | 동작 |
| --- | --- |
| 브라우저 임시 저장 | 뉴스·미디어·앨범·구단 안내의 입력을 700ms 후 자동 저장. 사용자 UUID/항목별 분리, 7일 만료, 로그아웃/저장/명시적 파기 시 삭제 |
| 임시 저장 복원 | 사용자가 선택해야 양식에 복원. 서버 버전이 달라졌으면 비교 안내. 개인정보용 선수 화면에는 적용하지 않음 |
| 서버 초안/승인 | 기존 초안·승인 대기·발행 유지. 새 RPC는 권한·입력 필드·현재 버전을 재검증하고 한 트랜잭션으로 저장 |
| 예약 발행 | JST로 지정, 현재 이후 1년 이내. 승인자·승인 시각·승인한 버전을 보관. 내용을 수정하면 이전 예약 취소 |
| 예약 실행 | 서버 전용 작업이 현재 승인자 권한, 내용 버전, 기존 사진·동의·필수 항목 조건을 재검사. 실패 시 발행하지 않고 확인 대상으로 표시 |
| 수정 이력 | 실제 저장부터 이력 생성. 도입 전 자료의 첫 수정은 수정 직전 상태를 기준본으로 기록하고 작성자/과거 날짜를 만들지 않음 |
| 복구 | 확인 후 비공개 초안으로 복구. UUID·이미 발행한 URL 유지, 철회된 사진 동의를 이전 true로 복구하지 않음 |
| 상태 안내 | 브라우저 임시 저장, 서버 저장, 예약, 실제 발행, 정적 사이트 반영을 구분. 목록의 예약 상태와 대시보드의 실패/지연 항목 표시 |

공개 중 콘텐츠를 초안·승인 대기·예약으로 저장하거나 과거 버전으로 복구하면 공개를 취소합니다. 화면에서 이를 설명합니다. 예약 중인 미디어도 같은 원칙을 따르므로 기존 공개에 사용하는 사진을 예약으로 돌릴 때 연결 기사에 영향을 줄 수 있습니다.

## 보안과 저장 범위

기존 DB 역할이 기준입니다. Owner/Administrator/Editor의 콘텐츠 권한을 유지하며 구단 안내는 Owner/Administrator만 편집합니다. 공개 프로필 승인 및 선수 내부 정보 권한은 변경하지 않습니다.

본문 이력과 예약 정보는 Data API에 노출하지 않는 private 스키마에 보관합니다. 익명·Coach·비활성 운영진에게 허용하지 않으며, 좁은 RPC가 매번 실제 DB 역할을 확인합니다. 목록은 현재 페이지의 ID 50개 이하에 대한 예약 메타데이터만 조회합니다. 전체 운영 데이터 다운로드 기능은 추가하지 않습니다.

복구 대상은 내용 변경입니다. 삭제한 DB 행이나 삭제된 원본 사진의 복구는 운영 백업 절차가 필요합니다. 브라우저 임시 저장은 서버 백업이 아니며 브라우저 데이터 삭제, 저장 공간 제한, 7일 만료 또는 로그아웃 시 사라집니다.

콘텐츠 이력은 항목별 최신 30개 중 최근 90일을 조회·복원합니다. 90일 지난 기록의 실제 삭제는 별도 일일 정리 작업으로 실행하므로, 작업 비활성 상태에서는 DB에 더 오래 남을 수 있습니다. 정리 작업 활성화와 상태 확인은 아래 적용 절차를 따릅니다. 기존 감사 로그에는 본문을 기록하지 않습니다.

## 운영 적용

1. PR #5(V2) → #6(일정) → 이 콘텐츠 PR 순서로 검토합니다.
2. 별도 개발 DB에서 새 마이그레이션과 테스트를 실행합니다. 운영 DB는 초기화하지 않습니다.
3. 운영 적용 승인 후 신규 콘텐츠 마이그레이션을 적용하고 새 프런트엔드를 배포합니다. 자동 임시 저장·이력·복구는 기능 감지 후 표시합니다.
4. 예약 발행은 처음에 비활성입니다. 담당자가 검토한 후 supabase/operations/enable-content-publisher.sql을 전용 프로젝트에 실행하고 Cron 실행 성공을 확인합니다. 실제 외부 메시지는 보내지 않습니다.
5. 활성화 후 관리자에 다시 로그인하면 예약 입력이 나타납니다. 초기 예약은 승인된 구단 자료로 담당자가 등록하고 상태와 홈페이지 반영을 확인합니다.

DB 발행 처리는 분 단위, GitHub Pages 재구축은 기존 약 15분 주기입니다. 작업 대기나 장애로 더 늦어질 수 있습니다. 예약 저장을 즉시 공개 완료로 표시하지 않습니다. 오류는 예약을 자동 재시도하지 않으며, 내용을 검토하고 다시 예약합니다.

롤백할 때는 먼저 예약 작업을 중지하고 활성화 값을 false로 설정합니다. 이전 프런트엔드로 전환해도 콘텐츠·이력 테이블을 삭제하지 않습니다.

## 검증

PostgreSQL 테스트는 권한 없는 저장/이력 조회, 오래된 버전 덮어쓰기, 복구 시 UUID·URL·초안 상태 유지, 예약 실행·중복 실행·수정/명시 취소, 승인자 비활성화, 미승인 사진, 동의 철회 복구 금지를 검사합니다. UI 테스트는 자동 저장 표시/로그아웃 정리/명시적 복원/JST 예약 요청/복구 확인을 검사합니다. 운영 자료를 테스트 레코드로 사용하거나 운영 DB에 가상 콘텐츠를 만들지 않습니다.

예약 기능의 실제 Supabase Cron 실행과 브라우저 픽셀 시각 검토는 운영 적용 전 확인할 항목입니다.

최종 로컬 결과: Astro/TypeScript 55개 파일에서 오류·경고·힌트 0개, 정적 페이지 11개 빌드 및 오프라인 내보내기 완료. 기존 DB 검사 28개, 일정 DB 검사 23개, 콘텐츠 DB 검사 37개, Node UI·날짜·공개 페이지 검사 30개 통과. 운영 Supabase에는 기존 마이그레이션 두 개만 적용되어 있으며 이번 추가 SQL은 미적용 상태입니다. 운영 보안 검사에서는 기존 유출 비밀번호 차단 설정 경고 1건이 확인되며 이번 변경과 관련된 새 경고는 없습니다. 신규 SQL의 보안 근거는 로컬 PostgreSQL 권한 검사이며 운영 적용 후 Advisors를 다시 실행해야 합니다.
