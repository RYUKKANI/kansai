# 선수 관리 프로그램 연동 설계 — 3~6단계

이 문서는 후속 개발의 변경안입니다. 이번 PR은 선수 데이터 구조를 변경하거나 내부 정보 조회를 개방하지 않습니다. 구현 범위는 V3 일정과 콘텐츠 운영까지입니다.

## 3단계: 현재 구조와 변경안

실제 마이그레이션에서 확인한 구조는 다음과 같습니다.

| 현재 저장소 | 역할과 접근 | 후속 변경안 |
| --- | --- | --- |
| public.players | 변경 불가 UUID, 관리용 이름, 활동 상태, 프로필/사진 동의. Owner/Administrator/Coach만 접근 | 기본 인물 식별의 기준 유지. 동의 확인 시각·범위·철회 시각을 별도 모델로 확장 |
| public.public_player_profiles | player_id가 players.id를 참조. 공개 이름·사진·소개·포지션·등번호·활동 상태·승인자·발행 상태 | 공개 승인된 표시 정보의 기준. 선수 등록과 별도 작업 유지 |
| private.player_contacts | player_id 기반 JSON 영역. 현재 모든 클라이언트 접근 차단 | 필요한 연락 수단만 명시적 열로 설계. 담당 업무별 조회 제한 |
| private.attendance | 훈련 UUID/선수 UUID 복합키, 출석 상태. 현재 클라이언트 접근 차단 | 실제 회차 ID를 유지하고 담당 코치에게 제한된 출석 API 제공 |
| private.player_evaluations | 선수 UUID/평가자/평가일/JSON 영역. 현재 접근 차단 | 코치 평가와 의료·컨디션을 같은 자료형에 섞지 않음 |
| public.match_events | 경기 UUID/선수 UUID/이벤트/분/세부 자료. 축구 운영진 접근 | 검증 전 원시 기록. 경기 출전/시즌 통계 공개 모델은 아직 없음 |

소속, 입단일·퇴단일, 시즌별 등번호의 정식 기준 데이터는 아직 완성되어 있지 않습니다. 현재 포지션·등번호는 공개 프로필에만 있습니다. 자료가 없다는 사실을 추정 값으로 채우지 않습니다.

제안하는 최소 확장:

- players: 불변 id와 내부 이름 유지. 외부 프로그램 ID는 별도 unique external_id 매핑으로 관리하고 PK를 교체하지 않습니다.
- player_memberships: player_id, team_id, starts_on, ends_on, status. 재입단은 기존 선수 ID에 새 소속 기간을 추가합니다. 종료일은 시작일 이상이어야 합니다.
- season_registrations: player_id, season_id, position, jersey_number. 선수의 시즌별 등록 데이터 기준입니다. 공개 프로필에는 승인된 표시본을 유지합니다.
- player_consents: player_id, scope(profile/photo), granted_at, withdrawn_at, verified_by, policy_version. 증빙 원문이 필요하면 별도 보호 저장소에 두고 공개 응답에는 포함하지 않습니다.
- 내부 연락처는 필요한 항목만 구조화하고 출석·평가·운영 메모와 서로 다른 조회 권한을 둡니다.

위 이름은 제안이며 마이그레이션을 작성하지 않았습니다. 실제 사용 항목과 담당자를 확인한 후 개발 DB에서 추가형 마이그레이션을 준비합니다. 기존 프로필 값을 기준 데이터로 옮길 때 담당자가 확인한 값을 사용하고, 확인되지 않은 입·퇴단일을 생성하지 않습니다.

## 4단계: 별도 프로그램 MVP

| 개발 묶음 | 실제 운영 흐름 | 완료 기준 |
| --- | --- | --- |
| A. 명부 | 선수 등록/검색, 활동/소속 상태, 기존 UUID로 식별 | 이름이 같은 선수·이름 변경·재입단을 구분, 중복 등록 확인, 공개 프로필 자동 생성 없음 |
| B. 출석 | 기존 training_sessions 회차 선택 → 선수별 present/absent/late/excused | 반복 회차별 기록 분리, 동시 수정 충돌 확인, 출석 수와 선수 명부 일치 |
| C. 경기 기록 | 경기 출전 명단·분·골/도움/카드 입력 → 담당자 검증 | 수정 이력, 삭제 대신 정정, 합계가 원시 기록과 일치 |
| D. 시즌 통계 | 검증된 경기에서 시즌별 집계 → 공개 승인 | 미승인 원시 데이터 제외, 재집계 가능, 출전·득점 중복 집계 방지 |
| E. 코치 업무 | 담당 선수의 평가 및 운영 메모 | 업무 범위에 따른 조회, 일반 콘텐츠 Editor 차단, 선수 홈페이지로 전송 없음 |

MVP에서는 의료 기록, 파일 대량 업로드, 외부 메시지 자동 발송을 수집·구현하지 않습니다. 후속 요구가 확인되면 별도로 설계합니다. 선수 단위 메모와 팀 전체 운영 공지를 구분해 불필요한 개인정보 복제를 줄입니다.

### 민감한 자료의 접근과 보관 제안

현재 Owner/Administrator/Coach/Editor 네 역할만으로 의료 자료까지 조회하게 만들지 않습니다. 별도 권한 부여 기록(user_id, capability, team/player scope, expires_at)을 검토합니다.

- 연락처: 선수 등록 담당자에게 필요한 열만 제공. 대시보드·일반 목록·로그에는 제외.
- 코치 평가: 담당 팀 코치와 지정 책임자에게만 공개. 운영 메모와 분리하고 다운로드를 기본 차단.
- 의료·컨디션: 별도 보호 스키마 및 지정 담당자 권한. 구단 Owner라는 이유만으로 원문 자동 조회 권한을 부여하지 않음.
- 권한 부여/회수/조회 기록은 변경 불가 감사 경로로 남기되 원문 평가·의료 내용을 로그에 넣지 않음.
- 보관 기준 초안: 활동 중 필요한 자료만 유지하고 시즌 종료 시 검토. 연락처는 퇴단 후 운영 목적 종료 시 삭제/최소화 검토, 평가는 시즌 종료 후 보관 필요성 검토, 의료 자료는 수집 전에 목적·담당자·삭제 시점을 별도로 확정.
- 삭제 요청 시 운영 원본, 파생 데이터, 임시 파일, 백업 만료까지 범위를 확인. 기간은 책임자 결정 전 자동 삭제 작업으로 활성화하지 않음.

## 5단계: Source of Truth와 연동

| 항목 | 기준 시스템 | 다른 화면의 사용 방법 |
| --- | --- | --- |
| 선수 UUID/관리 이름/소속/활동 상태 | 선수 관리 프로그램의 공통 DB 기본 명부 | 관리자에서 같은 ID를 조회, 홈페이지에는 관리 이름 자동 노출 금지 |
| 포지션/시즌 등번호 | 향후 시즌 등록 데이터 | 공개 편집의 기본값으로 가져오고 승인된 표시본으로 발행 |
| 표시 이름/공개 사진/소개/발행 상태 | Club Office 공개 프로필 | 홈페이지는 승인된 필드만 조회 |
| 동의/철회 | 선수 등록·동의 기록 | 승인 시 재검사. 철회는 공개 프로필과 관련 공개 파생 자료를 비공개로 전환 |
| 일정 | 기존 fixtures/training_sessions/club_events | 캘린더·출석·대시보드가 같은 레코드 참조 |
| 출석/코치 평가/연락처/내부 메모 | 비공개 선수 관리 영역 | 홈페이지 데이터 생성과 독립 |
| 경기 원시 기록 | match_events 및 후속 출전 기록 모델 | 검증 및 통계 승인 단계를 거쳐 공개 통계만 생성 |

입력 중복을 줄이되 승인 과정은 유지합니다. 예를 들어 명부의 등번호 변경은 공개 프로필 편집의 기본값/검토 항목으로 전달합니다. 승인 없이 공개 프로필을 덮어쓰지 않습니다. 공개용 표시를 별도로 정했다면 override 이유와 기준 데이터 버전을 기록합니다.

예상 흐름:

1. 선수 프로그램이 UUID를 발급해 기본 명부를 저장합니다.
2. Club Office가 해당 UUID로 공개 가능한 필드를 가져옵니다.
3. 동의·사진 게시 권한과 책임자 승인을 검사합니다.
4. 승인된 프로필만 기존 공개 API/정적 빌드에 전달합니다.
5. 경기 기록도 원시 기록 → 검증 → 시즌 집계 → 공개 승인 순서로 처리합니다.

### API 계약과 호스팅

브라우저 앱은 publishable key와 실제 사용자 세션을 사용합니다. 매 요청에서 활성 DB 역할/범위를 확인하고 RLS를 적용합니다. 서버 전용 키는 GitHub Pages 번들, localStorage, 공개 환경 변수, 로그에 넣지 않습니다. user_metadata는 권한 근거로 사용하지 않습니다.

명부/출석 API는 필요한 열만 반환합니다. 목록 페이지네이션, 업데이트의 expected_updated_at, idempotency key, 불변 UUID와 FK, 고유 제약으로 중복 및 동시 수정을 처리합니다. 공개 사이트가 내부 명부 API를 직접 호출하지 않게 합니다.

홈페이지는 기존 GitHub Pages 정적 빌드를 유지합니다. 공개된 데이터만 빌드 시 읽고 발행 버전 일관성을 검사합니다. 내용 수정은 약 15분 주기 배포로 반영되며 민감한 공개 철회 시 수동 재배포와 배포 상태 확인을 우선합니다. 기존 다운로드·방문자 캐시는 DB 철회만으로 회수할 수 없으므로 공개 전 동의가 필요합니다.

내부 프로그램은 로그인 후 RLS로 필요한 최신 운영 데이터를 조회합니다. 향후 실시간 점수판이 필요하면 공개 전용 읽기 모델만 별도로 연결합니다. 정적 호스팅의 서버 비밀키 보관 제약을 피하기 위해 보호 API는 Supabase 함수/서버에 둡니다.

## 6단계: 자동화와 운영

| 기능 | 시작 조건·데이터 | 통제 및 산출물 |
| --- | --- | --- |
| 일정 변경 알림 | 기존 회차의 실제 변경 이벤트 | 변경 요약을 검토하고 대상 팀·수신자·채널을 책임자가 승인 |
| 콘텐츠 승인 알림 | pending 전환 | 승인 담당자 그룹에만 발송, 본문/내부 개인정보 포함 금지 |
| 출석 집계 | 기록된 실제 회차와 명부 | 결측·취소·중복 회차를 구분, 월별 운영 보고서 |
| 시즌 통계 | 검증된 경기·시즌 등록 | 재현 가능한 집계, 공개 승인본/내부 원본 분리 |
| 변경 감사 | 인증된 실제 작업 | 주체·대상 ID·변경 필드·시각, 민감한 원문 제외 |
| 백업·복구 | DB와 보호 Storage | 암호화, 접근 제한, 별도 환경 복구 훈련, 보관 만료 관리 |
| 권한 점검 | 활성 멤버/담당 범위/세션 | 퇴임자 회수, 불필요한 역할 제거, 실제 RLS 차단 테스트 |

외부 전송은 outbox에 event_id, recipient_snapshot, template_version, approved_by, approved_at, state를 두는 방식을 제안합니다. 승인되지 않은 이벤트는 발송하지 않습니다. 전송 전 수신 대상과 담당자 권한을 다시 확인하고, 멱등성 키로 중복 발송을 막습니다. 실패는 재시도 횟수·백오프·최종 담당자를 정합니다. 이번 작업에서는 메일·메신저·SMS 서비스를 연결하거나 발송하지 않습니다.

백업 주기/비용/저장 위치는 담당자가 정합니다. 운영 DB를 공개 저장소나 Actions artifact로 내보내지 않습니다. 복구 훈련은 격리된 프로젝트에서 수행하고 Auth UUID, 역할, Storage, FK, 공개 승인 상태가 함께 복구되는지 확인합니다. 운영 교체와 삭제는 검증 결과를 승인한 뒤 진행합니다.

## 후속 개발의 승인 지점과 검증

3단계 필드/담당자 확정 → 개발 DB 마이그레이션 → 역할별 API·RLS 테스트 → 제한된 실제 운영 검증 → 별도 PR 순서로 진행합니다. 큰 DB 변경이나 실제 자료 이관을 이 설계만으로 실행하지 않습니다.

필수 검증 사례: 동명이인·재입단, 프로필과 사진의 동의 독립, 동의 철회 후 공개 차단, Editor/비활성/익명의 내부 접근 차단, 담당 범위 밖 평가 차단, UUID 변경 거부, 취소 훈련의 출석 집계 제외, 경기 통계 중복/수정 후 재집계, 외부 알림 승인 취소, 백업 복구 후 동일 권한 유지.
