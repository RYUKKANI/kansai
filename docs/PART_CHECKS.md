# 기능별 검사 실행

수정한 기능과 그 기능을 공유하는 파트만 검사합니다. 대시보드 수정 때문에 회원가입·선수·일정 검사를 모두 이어서 실행하지 않습니다. 공통 코드가 여러 기능에 영향을 주면 필요한 파트를 합쳐 선택하고, 결과도 파트별로 확인합니다.

## 파트 목록

실행 목록의 기준은 `scripts/test-parts.mjs`입니다. 아래 명령으로 현재 파트와 검사 수를 확인합니다. 파일별 배정은 manifest에서 확인합니다.

```sh
npm run test:parts
```

| 파트 ID | 검사하는 동작 |
| --- | --- |
| `dashboard` | 대시보드·운영 현황 |
| `auth` | 로그인·회원가입·비밀번호 설정·복구 |
| `members` | 회원 승인·등급·실명·계정 관리 |
| `content` | 뉴스·구단 안내·참가 안내·콘텐츠 번역 |
| `players` | 선수·공개 프로필·본인 선수 정보 |
| `schedule` | 경기·훈련·행사·반복 일정 |
| `media` | 사진·영상·앨범·편집 중인 미디어 |
| `public` | 공개 홈페이지·메뉴·사진 보기·경기 표시·정적 미리보기 |
| `security` | RLS·등급 경계·세션·보안 정책 |
| `tooling` | 검사 선택기·실행 목록·미리보기 내보내기 도구 |

공유 검사가 여러 파트에 들어갈 수 있습니다. 예를 들어 선수와 계정의 연결은 `members`와 `players`에서 함께 확인합니다. 동일한 테스트 파일은 한 번의 선택 실행 안에서 같은 fixture로 중복 실행하지 않습니다.

## 로컬에서 한 파트 수정하기

처음에는 `npm ci`로 의존성을 설치합니다. 대시보드를 고쳤다면 다음 한 명령으로 필요한 테스트용 빌드를 준비하고 해당 파트만 실행합니다.

```sh
npm run test:dashboard
```

모든 파트에 `test:auth`, `test:members`처럼 `test:<파트 ID>` 명령이 있습니다. 준비와 실행을 나누어 확인할 때는 다음 두 명령을 사용합니다.

```sh
npm run test:prepare -- --part dashboard
npm test -- --part dashboard
```

서로 연결된 두 파트를 바꿨다면 같은 선택을 준비와 실행에 사용합니다.

```sh
npm run test:prepare -- --parts members,players
npm test -- --parts members,players
```

`--part`를 반복해도 됩니다. 알 수 없는 파트나 서로 충돌하는 옵션은 실행 전에 실패합니다. `npm test`만 입력하면 목록과 사용법을 보여주고 종료합니다. 이 종료 코드는 실제 회귀 검사를 통과했다는 뜻이 아닙니다.

`npm test -- --part …` 실행기는 빌드를 자동 시작하지 않습니다. 필요한 빌드가 없거나 해당 테스트용 설정과 맞지 않으면 준비 명령을 안내하고 실패합니다. 준비 명령은 매번 선택한 파트에 필요한 fixture를 새로 빌드합니다. 한 번의 준비에서 여러 파트가 같은 fixture를 요구하면 한 번만 만듭니다. 기존 fixture의 소스 최신 여부까지 자동 판별하지 않으므로 화면 코드를 바꾼 뒤에는 준비 명령을 다시 실행하거나 `test:<파트 ID>` 명령을 사용합니다.

테스트용 fixture는 다음처럼 나뉩니다. 가짜 Supabase 연결값과 로컬 PostgreSQL 엔진으로 업무를 검사하며 운영 계정이나 운영 데이터는 변경하지 않습니다.

| fixture | 생성 위치 | 용도 |
| --- | --- | --- |
| `legacy` | `dist-legacy/` | 기존 관리자 흐름과 업무 UI |
| `identity` | `dist-identity/` | 아이디 로그인·회원 상태·등급 UI |
| `public` | `dist/` | 공개 페이지와 공통 공개 UI |
| `preview` | `preview/` | 파일 미리보기 내보내기 |

화면·번들에 영향을 주는 수정은 `npm run check`, `npm run build`, `npm run export:preview`도 확인합니다. 이 공통 빌드 확인은 타입·구문·정적 페이지·미리보기 생성 확인입니다. 다른 모든 업무의 회귀 검사를 실행했다는 의미는 아닙니다. 브라우저에서는 바꾼 기능의 실제 화면과 필요한 언어·모바일 동작을 확인합니다. 문서만 바꾼 경우에는 관련 문구와 링크를 검토합니다.

전체 회귀 검사가 명시적으로 필요한 경우에만 다음 명령으로 모든 fixture를 준비하고 등록된 모든 파트를 검사합니다. 일상적인 단일 파트 수정의 기본값은 아닙니다. 실제 Auth 검사는 아래의 별도 명령을 사용합니다.

```sh
npm run test:full
```

## GitHub Actions에서 선택하는 범위

CI는 `scripts/plan-checks.mjs`와 `scripts/checks-plan-lib.mjs`로 변경 파일을 읽고 파트 목록과 준비할 fixture를 계산합니다. PR은 기준 브랜치와 PR 끝 커밋의 `base...head`, push는 push 이전과 이후의 `before..head` 전체 범위를 비교합니다. 여러 커밋을 한 번에 push해도 마지막 커밋만 검사하지 않습니다. 파일 이동은 이전 경로와 새 경로의 영향을 모두 포함합니다.

`main` push에서 변경 파일만으로 범위를 좁히려면 `push.before` 커밋의 가장 최근 push 실행 시도에서 `Required part checks complete`가 완료·성공했음을 확인해야 합니다. 이전 기준이 미검증·실패·취소·누락 상태이거나 GitHub API에서 확인할 수 없으면 모든 파트 job과 실제 Auth 검사를 한 번 선택합니다. 뒤이은 문서 수정만으로 이전 코드의 실패가 통과로 바뀌지 않도록 하는 보호입니다. 검증된 기준에서 문서만 바꾼 경우에는 빌드·업무 검사를 계속 생략합니다.

선택한 파트마다 별도 matrix job이 실행됩니다. 파트가 열 개라고 해서 매번 열 개를 모두 실행하지 않습니다. 공통 코드나 DB 변경으로 여러 파트가 선택되면 각 파트의 결과를 따로 볼 수 있습니다.

| 변경 예 | 선택 원칙 |
| --- | --- |
| 대시보드 전용 코드·스타일 | `dashboard` |
| 선수 편집과 사진 선택 | 선수·미디어 등 실제 연결된 파트 |
| 로그인·권한·세션 처리 | 인증·회원·보안 등 영향 파트와 필요한 실제 Auth 검사 |
| 공통 관리자·언어·스타일 | 해당 코드를 사용하는 여러 파트 |
| DB 마이그레이션·검사 기반·의존성 | 공통 영향이 커서 여러 파트 또는 전체 파트로 확대 |
| 문서만 변경 | push 이전 기준의 성공이 확인되면 빌드·배포·업무 회귀 검사를 생략. 기준 미검증 시 모든 파트와 실제 Auth 검사 |
| 공개 콘텐츠 정기 재구축 | 콘텐츠 변경 시 `public`; 변경이 없으면 생략. 인증·회원 업무 검사를 반복 실행하지 않음 |
| 비교 기준이 없거나 새 코드 경로가 규칙에 없음 | 검사를 생략하지 않고 넓은 범위로 선택하고 이유를 출력 |

수동 workflow 실행은 `part`에서 검사할 파트를 고르며 기본값은 `dashboard`입니다. 전체 파트는 `all`을 명시해야 합니다. 공개 콘텐츠 반영을 위한 수동 실행에는 `public`을 선택합니다.

경로와 실제 선택 결과는 선택기 코드가 기준입니다. 별도 번역·스타일 파일은 실제 Auth 검사를 요구하지 않지만, 인증 UI의 마크업·동작 파일은 인증 경계를 함께 바꿀 수 있어 보수적으로 범위를 넓힙니다. 로컬은 파트를 명시적으로 선택하고 CI는 Git 비교로 자동 선택합니다. 실제 Auth 검사는 `npm run test:auth:native`로 분리되어 있으며, CI가 인증 서버·마이그레이션·세션·보안 경계 등 해당 변경에 필요할 때 실행합니다. 검증된 기준의 단순 공개 화면 수정이나 공개 콘텐츠 예약 재구축에는 실행하지 않습니다. 앞서 설명한 push 기준 검증 실패 때는 보수적으로 포함합니다. 이 검사는 Docker의 일회용 GoTrue 환경을 사용하므로 로컬 실행에는 Docker가 필요합니다.

## 게시 순서와 검증 보호

코드 변경·예약 재구축·수동 실행은 각각 다른 concurrency 그룹에서 검증하므로 예약 작업이 진행 중인 코드 검증을 취소하지 않습니다. 예약·수동 게시에는 같은 SHA의 가장 최근 push 실행 시도에서 `Required part checks complete`가 완료·성공한 결과가 필요합니다. 최신 시도가 실패했거나 진행 중이면 예전 성공을 재사용하지 않습니다.

실제 게시 작업은 별도 공개 잠금으로 직렬화합니다. 게시 가능 여부를 확인하고 잠금을 얻은 뒤에도 최신 `main` SHA를 다시 조회하며, 더 새 커밋이 있으면 이전 산출물의 게시를 생략합니다.

## 검사를 추가하거나 파일을 옮길 때

새 테스트를 만들면 `scripts/test-parts.mjs`의 해당 파트에 파일을 등록합니다. SQL 업무 검사는 `sql`, 일반 JavaScript/UI 검사는 `js`, 아이디 인증 설정의 번들이 필요한 검사는 `identity`에 넣고 필요한 fixture도 지정합니다. 기존 테스트를 삭제하거나 넓은 suite를 빠뜨려 검사 수를 줄이지 않습니다. 파일을 옮겼다면 manifest의 경로도 함께 바꿉니다.

새 소스 경로가 생기면 `scripts/checks-plan-lib.mjs`에 그 모듈을 사용하는 파트를 연결하고 `tests/checks-plan.test.mjs`에 선택 결과를 검증하는 사례를 추가합니다. 공통 모듈은 직접 수정한 화면뿐 아니라 호출하는 업무도 포함합니다. CI는 같은 manifest와 선택기를 사용하므로 별도의 테스트 파일 목록을 workflow에 복사하지 않습니다.

실행 목록의 누락 검사는 모든 기존 테스트가 최소 한 파트에 등록됐는지 확인합니다. 이 검사와 경로 선택기의 사례는 `tooling` 파트에서 검증합니다. 검사 기반을 바꾸는 작업 자체는 여러 파트에 영향을 줄 수 있으므로 각 파트를 순서대로 검증하고 결과를 구분해 보고합니다.

## 결과를 해석할 때

선택된 파트의 성공은 그 범위의 확인 결과입니다. UI 테스트의 대체 서버 응답은 실제 Supabase Auth 성공이나 실제 화면 배치를 보장하지 않습니다. 로컬 PostgreSQL 검사는 RLS와 DB 트랜잭션을 확인하고, 실제 Auth 검사는 일회용 인증 서버의 동작을 확인합니다. 운영 API 확인이나 운영 설정 점검이 필요한 변경은 별도 결과로 남깁니다.

검사 결과에는 선택한 파트, 실행한 테스트, 빌드 확인, 실제 브라우저 확인과 실행하지 않은 범위를 적습니다. 문서만 바꿨거나 `npm test`로 도움말만 본 작업을 전체 검사 통과로 보고하지 않습니다.
